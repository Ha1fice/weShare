# Spec：免密身份（设备指纹）——"简版"登录形态

- 来源：ha1fice/weShare#5
- 分支：`npc/3-device-identity`（基于 `main@3e94684`）
- 定位：在 1.0 的账号体系之外增加一种**可选**的入口形态，不替换密码登录

## 1. 要解决的问题

1.0 的第一道门是"注册/登录"，对试用和内部演示来说代价太高：要邮箱、要密码、要记住，
同事之间还要互发邀请。真正想验证的是"文档能不能用、协同顺不顺"，不是"密码会不会输"。

于是做成：**打开页面，输个名字，进去就能写。** 服务端用设备指纹派生一个稳定身份，
下次打开还是你。账号体系不删、不做简化——它退到后面，只在需要"把别人拉进同一个空间"
时才用。

## 2. 形态

```
用户打开页面
  ├─ 已有会话 Cookie ──────────────→ 直接进工作区
  └─ 没有会话
       ├─ 免密模式开 → /welcome：输名字 → POST /api/v1/auth/device → 进工作区
       └─ 免密模式关 → /login：邮箱密码（现状不变）
```

首次进入不是空页面：自动建一个「<名字> 的空间」+ 一篇「欢迎使用 weShare」文档，
用户落地即可点开写东西。

## 3. 身份 key 怎么定

- 客户端采集稳定的**低精度**指纹：时区、语言、屏幕尺寸×色深、CPU 核数、UA 大版本、触点数量。
- 再加一份 **localStorage 随机盐**（16 字节）。盐负责把同型号的两台机器区分开，
  指纹负责在盐丢失（清缓存/换存储分区）后仍尽量把人认回来。
- `deviceKey = sha256("weshare-device-v1|" + traits + "|" + salt)`，64 位 hex。
- 服务端不建新表：`userId = "du_" + sha256("weshare-device-user:" + deviceKey)[0..32]`，
  占位邮箱 `<deviceKey 前 32 位>@device.weshare.local`（`.local` 不可路由，邮件流程不会误发）。
  同一 deviceKey 永远映射到同一账号，天然幂等。

刻意**不采集** canvas / WebGL / 字体列表：那类指纹精度高到可以当追踪器用，
而这里只需要"把自己认出来"，认错了也只是换了个新身份。

## 4. 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/auth/device` | `{ deviceKey, displayName }` → 会话 Cookie + 用户；首次 201（`created: true`），已存在 200 |
| POST | `/api/v1/auth/device/bind` | 登录态下把设备绑到当前账号；绑到他人 409 |

- 两条路由**只在 `DEVICE_IDENTITY=true` 时注册**，关闭时 404。密码登录、注册、`/me` 全部不受影响。
- 同一 deviceKey 重新输入名字 = 改名（简版里没有别的改名入口）。空间名不跟着改。
- 被禁用的账号返回 403，不能靠重新输名字绕过。
- 会话轮换：不沿用任何旧会话，与密码登录一致。

## 5. 开关

| 位置 | 变量 | 作用 |
|---|---|---|
| api | `DEVICE_IDENTITY=true` | 注册身份路由 |
| web | `VITE_DEVICE_IDENTITY=true` | 首屏换成 `/welcome`，守卫与登出改道 |

默认都关。两边不同步时前端会自然回落到登录页（接口 404 → 会话仍匿名）。

开关的落地方式：代码默认值与 `.env.example` 都保持 `false`，试用环境另有
`.env.trial.example` 模板（唯一差异是这两项为 `true`），部署说明见
`docs/deployment.md`。**不把试用配置写进默认值**——默认值会被照抄到生产。

免密模式下页脚不显示「用账号登录」：守卫会把已登录用户从 `/login` 送回首页，
免密用户又没有密码账号，那条链接点下去只会在原地打转。改成一句模式说明。

## 6. 安全边界（必须写明，不许含糊）

1. **deviceKey 不是凭证。** 知道别人 deviceKey 的人可以冒充他拿到会话。指纹可伪造、盐可复制。
2. 因此这套东西只适合**内网、单机、试用**。生产请保持 `DEVICE_IDENTITY=false`，走邮箱密码。
3. 占位邮箱不可用于登录：密码哈希写的是不可校验的哨兵值，任何密码都验不过。
4. 空间隔离不受影响：身份只回答"你是谁"，能不能读某篇文档仍由 `effectiveRole` + ACL 在服务端判定。
5. 错误信息与响应里不出现完整 deviceKey（服务端只展示由它派生的不可路由地址，自身不记录）。
6. 换浏览器/清缓存 = 新身份新空间，旧内容仍在原身份下。要跨设备继续用，需要密码账号（邀请走邮箱）。

## 7. 验收标准

- AC-D1 首次打开只有"输个名字"一个输入框，空名字不能提交（是/否）。
- AC-D2 提交后落到工作区，空间里已有欢迎文档，可打开（是/否）。
- AC-D3 同一浏览器刷新/重开，身份与空间不变（是/否）。
- AC-D4 换一个浏览器 → 新身份、新空间，看不到前一个身份的内容（是/否）。
- AC-D5 重新输名字 = 改名，身份与空间不变（是/否）。
- AC-D6 `DEVICE_IDENTITY=false` 时 `/api/v1/auth/device` 404，密码登录/注册照旧（是/否）。
- AC-D7 被禁用身份返回 403（是/否）。
- AC-D8 自动化：api 11 项集成测试 + web 9 项单测/组件测试通过（是/否）。

## 8. 不在本次范围

- 跨设备迁移身份（需密码账号或一次性迁移码）
- 设备列表管理 / 踢下线
- 指纹服务端二次校验（当前完全信任客户端提交的 deviceKey）
- 与 1.0 视觉方案（token / 基础组件）合并——`/welcome` 暂用现有工程样式
