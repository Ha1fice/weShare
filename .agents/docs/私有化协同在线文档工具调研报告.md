# 企业私有化协同在线文档工具技术调研报告

> 调研日期：2026-11-03。GitHub star/fork/活跃度数据均来自 GitHub API 当日抓取，为近似值；文中所有"估算"均已标注。
> 目标：为企业搭建「可私有部署、纯局域网可用、Web 端多人实时协同」的在线文档工具，优先支持 .docx/.xlsx 的导入/在线编辑/导出，长期对标腾讯在线文档（私有化版本），基于成熟开源项目二次开发。

---

## 1. 结论（一句话推荐）

**主选「混合架构」：第一阶段用 ONLYOFFICE Document Server 作为高保真 docx/xlsx 协同引擎（不改其源码、仅通过 DocsAPI/WOPI 集成，规避 AGPL 风险），配自建文件/权限/版本宿主服务快速上线；同时并行孵化基于 Yjs + Tiptap + Hocuspocus（全 MIT）的轻量协同文档与基于 Univer 的轻量表格，逐步把轻编辑场景迁移到自研原生编辑器，最终向腾讯文档形态演进。**

- 备选 A：**Univer Pro 一站式**（Apache-2.0 内核 + 商业授权，协同/导入导出/图表均在商业版，$99/月起，支持完全离线私有部署）——适合愿意付费换统一 Web 原生技术栈的团队。
- 备选 B：**Collabora Online + Nextcloud Office**——保真度与权限/版本体系最完整（MPL-2.0 商用友好），但瓦片渲染体验重、规模化需订阅，适合"保真与合规优先、体验可妥协"的场景。
- 明确不建议：Luckysheet（已归档）、x-spreadsheet（停更）、Y-Sweet（维护趋停）、CryptPad（组织权限弱、AGPL）作为企业基座。

## 4. 两条技术路线的边界

### 4.1 路线 A：服务端渲染型 Office（ONLYOFFICE / Collabora）

**原理**：文档解析与渲染在服务端完成（Collabora 渲染为栅格瓦片下发；ONLYOFFICE 服务端处理文档模型、前端 DOM 编辑），浏览器本质是"远程视图"。

**适用边界（何时必选）**：
- 复杂排版 Word（公文、合同、法律文件）必须高保真还原；
- 需要复用桌面 Office 内核的格式滤镜（.doc/.xls/.wps 等遗留格式）；
- "与桌面 Office 所见即所得一致"是硬性验收指标；
- 团队没有能力/预算自研格式引擎，需要最快上线。

**代价**：
- 资源重：Collabora 每文档一个进程，内存随并发文档线性增长（官方容量规划约 10 用户/CPU 线程、50MB RAM/用户）；
- 体验上限：瓦片流有延迟、缩放清晰度受限、**离线完全不可用**（Collabora 官方 FAQ 明确）；
- 许可证风险：ONLYOFFICE 社区版 AGPL + 20 并发硬限；Collabora CODE 官方不建议生产、规模化需订阅；
- 二开难度：C++ 内核 + 多仓库构建，UI 深度定制几乎不可行。

### 4.2 路线 B：Web 原生编辑器型（Univer / Yjs+ProseMirror/Tiptap）

**原理**：编辑器是纯前端应用，文档模型在浏览器内，协同靠 OT/CRDT 同步增量。

**适用边界（何时选）**：
- 轻量文档（会议纪要、Wiki、任务型文档）与轻量表格（数据收集、排期表）场景；
- 追求体验（离线可用、秒开、像素级 UI 定制、移动端友好）；
- 长期自研演进、需要完全掌控代码与许可证干净（MIT/Apache-2.0）；
- 需要与业务系统深度集成（嵌入、API 化）。

**代价（现实差距）**：
- docx/xlsx 保真是最大缺口：Univer 官方明示复杂公式/图表/字体/嵌入对象可能有差异；Tiptap 的 docx 转换为付费 Pro 且官方声明 round-trip 非字节级一致；
- 公式引擎、图表、数据透视表要么缺失要么在商业版（Univer 的图表/透视表/导入导出/协同全在 Pro）；
- 表格协同没有成熟的开源"类 Excel 编辑器"积木，需自研或采购。

### 4.3 结论

单一路线都无法同时满足"高保真 + 可自研演进"。**对标腾讯文档的正确姿势是混合架构**：保真场景（复杂 docx/xlsx 的编辑与往返）走服务端渲染或商业引擎，轻编辑场景（占日常 80% 流量）走 Web 原生自研，逐步迁移。

## 5. 重点方案详细分析

### 5.1 ONLYOFFICE Document Server（服务端渲染型首选）

- **版本与许可证**：社区版 AGPL v3、免费。官方定位社区版"最多 20 用户（推荐）"，并技术限制为 **20 个并发编辑连接**；移动端 Web 编辑器、白标、集群/高可用、Admin Panel、SLA 均为商业版（Enterprise/Developer）专属。JWT 鉴权、文档转换服务、插件/宏、协同功能全版本可用。（[版本对比](https://www.onlyoffice.com/en/compare-editions)、[官方许可 FAQ](https://helpcenter.onlyoffice.com/docs/faq/docs-community.aspx)）
- **AGPL 义务（官方 FAQ 口径）**：修改软件须公开修改后源码；用户通过网络使用须能获得源码；衍生作品须 AGPLv3。**未修改、纯内网自用不触发开源义务**；一旦修改 ONLYOFFICE 本体并对外以网络服务提供，修改部分须开源；不想开源则购买商业许可。
- **docx/xlsx 兼容**：官方口径为"原生 OOXML、围绕 OOXML 构建、无需转换"（[官方页面](https://www.onlyoffice.com/best-microsoft-office-alternative)）。已知短板：**不支持 VBA 宏**（宏用 JavaScript 实现，官方无 VBA 支持计划，仅提供 AI 转换工具）；数据透视表支持；复杂 Excel 场景社区普遍反馈弱于桌面原生（估算）。
- **协同实现**：中心化"文档编辑服务"转发合并变更（[co-editing 文档](https://api.onlyoffice.com/docs/docs-api/get-started/how-it-works/co-editing/)），官方未明示 OT/CRDT 字样；快速模式（默认）变更实时可见、自动保存，严格模式各自独立会话、保存前互不可见。
- **部署**：`onlyoffice/documentserver` Docker 镜像，JWT 默认开启；官方最低硬件双核 2GHz / 4GB RAM / 40GB 磁盘；集成走 DocsAPI（api.js + document.key）或 WOPI（v6.4+）；中文字体通过 `docker cp` 注入 `/usr/share/fonts/` 后执行字体生成脚本刷新（[字体文档](https://helpcenter.onlyoffice.com/docs/installation/docs-install-fonts-docker.aspx)）。
- **协作能力**：全版本含批注、内置聊天、审阅/修订跟踪、版本历史、文档比较/合并。移动端浏览器编辑器为商业版专属。
- **二开评估**：源码多仓库（core/server/web-apps）、构建链复杂（估算）；**只要不改 ONLYOFFICE 本体、仅通过 API 集成，自研宿主部分可闭源**——这是规避 AGPL 的关键操作姿势。

### 5.2 Collabora Online / LibreOffice Online

- **许可证**：代码以 MPL-2.0 为主（部分组件其他许可，[GitHub README](https://github.com/CollaboraOnline/online)、[官方 FAQ](https://www.collaboraonline.com/faqs/)）。MPL-2.0 为文件级 copyleft：修改的 MPL 文件须开源，但可与专有代码组合，**商用/闭源集成友好度显著优于 AGPL**。
- **CODE vs 企业版**：CODE 免费、滚动更新、无 SLA，官方定性"测试/家用/小团队"、不建议生产；开发构建会提示"限制 10 文档 / 20 连接"（社区材料佐证）。企业版按用户数年订阅、无用户数上限、含 SLA/长期支持。
- **与 LibreOffice Online 的关系**：LO Online 由 Collabora 主导开发，2022 年被 TDF 归档；**2026-02 TDF 宣布重启**但不提供托管与企业支持，仓库处于恢复早期（[TDF 博客](https://blog.documentfoundation.org/blog/2026/02/24/libreoffice-online-a-fresh-start/)）。当前成熟活跃主线仍是 Collabora Online。
- **保真度**：LibreOffice 内核滤镜，支持 DOC/DOCX/XLS/XLSX/PPT/PPTX/RTF 及宏格式（在线版禁用宏），兼容格式面最广；代价是服务端瓦片渲染——"像高效远程桌面而非浏览器应用"，需持续网络连接、离线不可用；24.04 版瓦片压缩提速 18 倍。
- **协同**：2016 年 2.0 版起支持实时协同；每文档一个独立 Kit 进程（jail 隔离），内存随并发文档增长。
- **部署**：`collabora/code` Docker 镜像，需反向代理 + 子域名 + SSL；**必须有 WOPI 宿主**（Nextcloud/ownCloud/自研）——存储、认证、权限全部由宿主承担；官方容量规划约 10 用户/CPU 线程、50MB RAM/用户 + 1GB 系统、100kbit/s 带宽/用户。
- **中文与移动端**：中文字体挂载到容器字体目录后重启（社区方案）；移动端有 Android/iOS 应用 + 浏览器响应式。
- **二开**：C++ 内核，构建/调试门槛高（估算），适合集成而非改造。

### 5.3 Nextcloud Office（一体化备选）

- 组成：Nextcloud Server（AGPLv3）+ richdocuments 集成应用 + Collabora 后端；网盘侧文件管理/共享权限/版本历史（≥2 分钟生成一版、自动过期）/审计日志成熟，可设 OOXML 为默认新建格式。
- 注意：Nextcloud 35 管理手册中默认方案已改为 "Nextcloud Office powered by Euro-Office"（独立 Document Server），Collabora 仍为完全支持的替代（[Office 手册](https://docs.nextcloud.com/server/stable/admin_manual/office/)）。
- 评估：开箱即用的"网盘 + 协同办公"闭环，全 AGPL 内网自用无商业限制；短板是瓦片渲染资源重、编辑器 UI 深度定制难、与 Nextcloud 应用生态耦合增加运维成本。适合作为"快速验证 + 权限体系参考"，不适合作为深度自研基座。

### 5.4 Univer（Web 原生型首选基座）

- **许可证结构（关键）**：核心仓库 Apache-2.0（开源范围：核心 SDK、插件系统、渲染引擎、公式引擎、Facade API、主题、i18n）；**实时协同、编辑历史、导入导出、打印、图表、透视表、迷你图、形状、服务端计算、企业部署包全部属于 Univer Pro 商业层**（`@univerjs-pro/*`，[商业授权协议](https://pro.univer.ai/license)、[Pro 文档](https://docs.univer.ai/guides/pro)）。
- **定价（2026-11-03 查）**：Free Trial 带水印、3 协同连接、10 次导出/月；Business $99/月或 $1,000/年起（25+ 连接、500+ 导出/月）；Enterprise 定制不限。按"编辑连接数 + 导出次数"计费；**自托管可完全离线、本地校验 license、无遥测**（[pricing](https://univer.ai/pricing)）。
- **Apache-2.0 的含义**：内部私有部署、二开、对外商业化均允许，无 copyleft 义务（须保留声明，含专利授权）；但 Apache-2.0 §6 不授予商标权。
- **产品形态**：Sheets/Docs/Slides + 关系表/PDF 六工具一运行时；官方宣称 500+ 函数、31 种图表、千万单元格渲染（宣传口径）。自托管协同方案为 Univer Pro Server（Server SDK），一键 Docker Compose、支持离线镜像包与 K8s Helm（[server 文档](https://docs.univer.ai/guides/pro/server)）；开源参考应用 [univer-workspace](https://github.com/dream-num/univer-workspace) 提供目录/权限/回收站工作台。
- **导入导出保真**：Sheets 导入 xls/xlsx/csv/tsv、导出 xlsx/csv/tsv；Docs 导入 doc/docx、导出 docx；依赖服务端 `@univerjs-pro/exchange-node`（Pro 能力）。官方坦承"复杂公式、图表、字体、嵌入对象可能有差异，不支持的元素可能被丢弃，请用真实文件验证"。第三方封装反馈导出时图片/完整条件格式/透视表不能完美往返（社区反馈，估算）。
- **协同**：自研 **OT**（"spreadsheet-specific OT collaboration algorithm，支持 200 并发编辑者"，官方口径）。
- **中文与兼容**：DreamNum 为 Luckysheet 原班中国团队，i18n 含 zh-CN/zh-TW；浏览器目标 Chrome/Edge ≥88、Firefox ≥90、Safari ≥14.1。
- **二开**：TypeScript 插件架构 + Facade API（浏览器/Node 同构），文档体系完整；学习曲线中等（插件模式需组合十余个包）。

### 5.5 Luckysheet 与 x-spreadsheet（历史参考）

- Luckysheet：MIT、16.6k 星，**仓库已归档**，README 首行官方声明不再维护、生产请使用 Univer。其价值在于验证了"开源表格引擎"的需求，技术遗产由 Univer 继承。
- x-spreadsheet：MIT、14.6k 星，轻量组件（基础格式/少量函数/数据验证），xlsx 读写依赖 SheetJS，无协同，2024-08 后基本停更。两者均不适合作企业基座。

### 5.6 CryptPad（高保密旁路场景）

- AGPL-3.0；端到端加密、服务器零知识（[白皮书](https://blueprints.cryptpad.org/_assets/document/whitepaper/main.pdf)）；协同引擎 ChainPad（patch + 哈希链、客户端合并）。
- 文档/表格/幻灯片能力来自**集成的 OnlyOffice 客户端代码**（非 Document Server）；docx/xlsx 支持导入/导出，内部存自有加密格式，非原生编辑；Safari 不支持。
- 企业短板：零知识导致管理员不能重置密码、不能审计内容；权限以文档 owner + 团队角色为中心，缺组织级细粒度权限。适合高保密轻协作旁路，不适合企业文档平台主基座。

### 5.7 Etherpad（轻量文本协同参考）

- Apache-2.0，Node.js 纯文本实时协同，协同内核 EasySync 为自研 OT、OT 工程化发源地之一；官方称可扩展至数千并发；插件生态成熟、Docker 部署成熟；v3 起 DOCX 导入/导出开箱即用（纯 JS 转换器）。
- 局限：仅富文本，无表格/公式/图表。价值：轻量文本协同兜底 + OT 工程实现参考。

### 5.8 Yjs + Tiptap/ProseMirror + Hocuspocus（自研轻量文档的最佳积木）

- **Yjs**：CRDT 框架，**MIT 确认**（README 明确，GitHub 的 NOASSERTION 为误报）；支持离线编辑、版本快照、共享光标；crdt-benchmarks 显示大文档性能良好；生产用户含 Linear、Nextcloud、Typst、Proton Docs 等。
- **Tiptap**：Editor 核心 MIT；付费边界为 Pro 扩展（私有 npm）与云；**docx 转换（Conversion）是 Pro 包，最低 $49/月**，支持导入 DOCX/Markdown、导出 DOCX/PDF/ODT 等，但官方明示 round-trip 非字节级一致（[Conversion 文档](https://tiptap.dev/docs/conversion/getting-started/overview)）。
- **ProseMirror**：MIT；2026-04 起 GitHub 仓库变为转发 stub，开发迁至作者自建 Forgejo，作者明确"会继续维护"，处于稳定维护期（[迁移公告](https://discuss.prosemirror.net/t/prosemirrors-migration-to-forgejo/8974)）。
- **Hocuspocus**：MIT、完全免费的自托管实时协同引擎（Yjs WebSocket 后端）；官方 Redis 扩展支持多实例水平扩展（注意 Redis 用于同步而非摊薄 CPU）；数据库/S3 持久化扩展；`onAuthenticate` hook 鉴权；不绑定 Tiptap，任何 Yjs 客户端可用。**纯内网部署路径清晰，是本报告推荐的协同底座。**
- **Y-Sweet**：MIT，Rust 版 Yjs 后端；母公司被收购后 OSS 维护放缓，新项目不建议。

### 5.9 APITable / NocoDB（多维表格类）

- **APITable**：AGPL-3.0；Airtable 类多维表格，API-first、canvas 渲染、自研 OT、宣称 10 万+ 行实时协同；是独立产品而非可嵌入组件，与"文档工具"目标距离较远，但其 Changeset/Operation/Snapshot 数据库原生架构值得自研表格时借鉴。
- **NocoDB**：数据库转表格视图。**许可证重要变化：自 2026-01-09 起整体改为 Sustainable Use License（fair-code）——仅限内部业务/非商业使用，对外商业化需商业授权**；此前版本为 AGPL-3.0（[官方许可说明](https://telemetry.nocodb.com/docs/self-hosting/license)）。选型时务必注意版本与许可证对应关系。

## 6. 许可证风险专题

### 6.1 AGPL-3.0 对"私有部署"意味着什么

- AGPL 相对 GPL 的唯一额外条款是第 13 条（网络交互条款）：**如果你运行修改后的程序并让其他用户通过网络与其交互，你必须向这些用户提供修改版的源码**（[GNU AGPL 中文全文](https://gnu.ac.cn/licenses/agpl-3.0.html)、[Why Affero GPL](https://www.gnu.org/licenses/why-affero-gpl.fr.html)）。
- 分场景结论：
  | 场景 | 义务 | 风险等级 |
  |------|------|---------|
  | 未修改、公司内部自用 | 无开源义务 | 低 |
  | 修改后、仅内部员工使用 | 严格解读下须向"该服务的用户"（含员工）提供修改部分源码（[Orangescrum 许可 FAQ 解读](https://helpdesk.orangescrum.com/guide/community/project/licence)） | 低-中（内部可控） |
  | 修改后、对外部客户/公众提供服务 | 必须向外部用户提供源码 | **高（闭源商业化不可接受）** |
  | 分发（交付部署包给客户） | 触发完整 GPL 类义务（附源码） | 高 |
- 实操要点：**通过 API/iframe/WOPI 集成（不修改 AGPL 程序本体）通常不构成衍生作品**，自研宿主可闭源；但对 AGPL 程序本体打补丁、插件深度耦合则需谨慎，最终解释权在法务，商业化前建议取得商业许可（ONLYOFFICE/CryptPad/Docmost 均提供）。
- 参考：中国信通院《从 MongoDB 更换开源许可协议谈开源软件法律风险》对 GPL/AGPL/SSPL 的对比分析（[PDF](http://ictp.caict.ac.cn/CN/article/downloadArticleFile.do?attachType=PDF&id=432)）。

### 6.2 各方案许可证要点速查

| 方案 | 许可证 | 私有部署自用 | 修改后内部用 | 对外商业化 |
|------|--------|-------------|-------------|-----------|
| ONLYOFFICE 社区版 | AGPL-3.0 | ✅ 免费，但限 20 并发连接、无移动 Web | ⚠️ 修改部分须向用户提供源码 | ❌ 需商业许可 |
| Collabora Online | MPL-2.0 为主 | ✅（CODE 不建议生产） | ⚠️ 修改的 MPL 文件须开源，可与闭源组合 | ✅ 相对友好；规模化建议订阅 |
| Nextcloud | AGPL-3.0 | ✅ | ⚠️ 同 AGPL | ❌ 需商业许可 |
| Univer 核心 | Apache-2.0 | ✅ | ✅ 无 copyleft | ✅（保留声明；商标不授权） |
| Univer Pro | 商业授权 | ✅ 付费，支持完全离线 | 按商业协议 | 按商业协议 |
| CryptPad | AGPL-3.0 | ✅ | ⚠️ | ❌ 需商业许可 |
| Etherpad | Apache-2.0 | ✅ | ✅ | ✅ |
| Yjs/Tiptap 核心/ProseMirror/Hocuspocus | MIT | ✅ | ✅ | ✅ |
| Tiptap Conversion/Pro | 付费订阅 | 付费 | — | 按订阅 |
| APITable / Docmost | AGPL-3.0（+商业 EE） | ✅ | ⚠️ | ❌ 需商业许可 |
| NocoDB（≥2026-01） | Sustainable Use License | ✅ 仅内部业务 | ⚠️ 不可对外商用 | ❌ 需商业授权 |
| Outline | BSL 1.1 | ✅ | ⚠️ 禁止作为"文档服务"对第三方商业提供；每版 4 年后转 Apache-2.0 | ❌（4 年内） |

### 6.3 三个最常被误读的点

1. **ONLYOFFICE 社区版的 20 并发**：是技术硬限（并发编辑连接数），不是"20 个注册用户"；超过必须购买 Enterprise/Developer 许可。
2. **Univer 开源版 ≠ 可用的协同文档产品**：协同、导入导出、图表、透视表都在商业层；纯开源版只是编辑器内核。评估成本时按 Pro 授权计价。
3. **NocoDB 已不是 AGPL**：2026-01 起新许可证限制对外商业使用，很多旧评测文章的许可证结论已过时。

## 7. 推荐方案与演进路径

### 7.1 推荐：混合架构（主选）

**第一阶段（0-3 个月）——快速上线高保真 Office 协同**
- 部署 ONLYOFFICE Document Server（Docker，内网）；≤20 并发用社区版验证，超过或需要移动端 Web/集群则采购 Enterprise 许可。
- 自建最小宿主服务：文件存储（MinIO）+ 元数据/权限/版本（PostgreSQL）+ 通过 DocsAPI（或 WOPI）对接；**不修改 ONLYOFFICE 本体，规避 AGPL**。
- 交付物：浏览器打开 docx/xlsx 多人协同编辑、导入导出、版本历史、权限控制。

**第二阶段（3-12 个月）——孵化自研轻量协同层**
- 轻量文档：Yjs + Tiptap（或 ProseMirror）+ Hocuspocus（全 MIT），覆盖会议纪要、Wiki、任务文档等轻场景；
- 轻量表格：基于 Univer 开源内核（Apache-2.0）或 Yjs 共享类型自研，参考 APITable 的 Operation/Snapshot 架构；
- 统一鉴权（SSO）、统一文件入口，按文档类型路由到不同引擎。

**第三阶段（12 个月+）——向腾讯文档形态演进**
- 自研原生编辑器逐步扩大覆盖，服务端渲染引擎收缩为"复杂格式导入导出/高保真转换"服务（可替换为 LibreOffice headless 做格式转换兜底）；
- 补齐腾讯文档企业版的关键能力：细粒度权限（可看/可编/可管理/评论/导出复制下载控制）、版本与操作留痕审计、组织架构集成、自定义模板与品牌（对标项见 §8）。

### 7.2 备选

- **备选 A：Univer Pro 一站式**。若团队希望统一 Web 原生技术栈、接受商业授权费（$99/月起、支持完全离线），用 Univer Sheets/Docs + Pro Server 一步到位。风险：保真度需 PoC 验证；核心能力绑定商业授权，长期成本与供应商依赖需评估。
- **备选 B：Collabora Online + 自研/Nextcloud WOPI 宿主**。若保真度与格式覆盖面是第一优先级、且可接受瓦片渲染体验与（规模化时的）订阅费用。MPL-2.0 对商业化比 AGPL 友好。

### 7.3 为什么不选其它

- Luckysheet/x-spreadsheet：已死或停更；
- CryptPad：组织权限弱、零知识导致无法审计、AGPL；
- Etherpad：仅纯文本，只能作旁路；
- APITable/NocoDB：多维表格/数据库产品，不是文档编辑器（且 NocoDB 许可证已收紧）；
- Outline/Docmost：知识库形态，无 xlsx、docx 导出能力弱，许可证对对外商用有限制。

### 9.2 局域网部署要点

| 事项 | 做法 |
|------|------|
| 离线镜像 | 外网机 `docker save` 或同步到 Harbor 私有 registry；字体包、npm/pnpm 离线包同理预置 |

| 无公网依赖 | 关闭所有遥测/更新检查；Univer Pro 支持本地 license 校验；注意 Tiptap Conversion 等付费组件的离线授权条款 |

| 备份 | MinIO 版本化 + PostgreSQL 定期 dump + 协同文档 Yjs 快照 |

## 10. 下一步验证计划（PoC）

| # | PoC | 内容 | 验收标准 |
|---|-----|------|---------|
| 1 | ONLYOFFICE 内网 Docker 部署 + 并发压测 | 离线镜像部署、JWT 开启、注入中文字体；模拟 20 人同时编辑同一 docx/xlsx | 20 并发编辑 30 分钟无掉线/丢字；编辑延迟体感 <1s；中文排版与字体正常；断网重连后变更不丢失 |
| 2 | docx/xlsx 保真度测试集 | 准备 15-20 份真实复杂文件（多级编号/页眉页脚/修订批注的 Word；公式/图表/数据透视表/条件格式的 Excel），ONLYOFFICE 与 Univer 各做 导入→编辑→导出 往返 | 制定保真度 checklist（≥20 项），往返后逐项比对；整体通过率 ≥90%，或明确列出可接受差距清单并获业务确认 |
| 3 | Univer 打开复杂 xlsx + 协同 | Univer Pro（试用授权）Docker Compose 离线部署；10 人并发编辑含公式/图表的 xlsx | 公式计算结果与 Excel 一致（抽样 50 个单元格）；协同冲突合并正确；导入导出闭环可用；记录与 Excel 的差异项 |
| 4 | Yjs + Tiptap + Hocuspocus 轻文档协同 | 搭建最小轻文档服务（鉴权/持久化/Redis）；50 人并发编辑同一文档 | 50 并发无冲突丢失；断线重连自动合并；服务重启后文档可恢复；单实例资源占用 <2 核 2GB |
| 5 | 纯局域网基础设施验证 | Harbor 离线镜像 + 内网 DNS + 自签 HTTPS + 转换服务（ONLYOFFICE Converter / LibreOffice headless） | 从裸机到全部服务可用全程零公网访问；docx→PDF 转换成功；移动端浏览器（内网 Wi-Fi）可打开编辑 |

建议顺序：1 → 2 → 5 可并行；2 的结果决定主引擎取舍；3、4 决定第二阶段自研路线的投入比例。
